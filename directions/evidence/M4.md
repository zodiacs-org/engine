# M4 angle conjunction evidence

This milestone adds `angleConjunctionArc`, a pure solver for direct
conjunctions to fixed meridians and the geometric horizon. It builds on the
directions checkout at `94fdb0e`. The engine source, root package and build
output are unchanged.

## Independent geometry

[M4-derivations.md](M4-derivations.md) gives the rotation equation and
separate rising, setting, upper-meridian and lower-meridian targets.
[angle-examples.ts](angle-examples.ts) contains authored equatorial and
oblique sphere examples with the intermediate geometry and independently
calculated arcs. Expected values are not derived from this library or an
ephemeris. The fixture comparison allowance was fixed before comparisons
with the solver and is enforced by [angles.check.ts](../checks/angles.check.ts).

The examples exercise both observer hemispheres, matching and opposite
declination signs, above-horizon and below-horizon positions, and contacts
on either side of the signed hour-angle seam. Exact equatorial contacts
return zero, while an already passed axis requires the next westward
passage. Arcs exceeding a half turn remain forward rotations. These checks
establish agreement on the authored examples only, not a global numerical
bound or physical accuracy.

Ptolemy's angular treatment and Placidus's westward direct construction
supply the named historical basis. The relevant passages were fetched and
read again for this milestone, as recorded in
[source-readings.json](source-readings.json). The role-swap converse choice
is refused for every angular target, following Placidus's restriction.
This solver enables no zodiacal aspect rays to angles.

## Rounding and domain limits

An independent implementation review identified cancellation across the
lower-meridian seam: direct subtraction could erase a small positive IC
arc. The solver now evaluates short wrapped arcs through two nonnegative
gaps, and tests enforce the exact independently derived gap. Long wrapped
arcs use direct turn addition to avoid unnecessary double rounding.
The unreduced difference remains rounded audit metadata, so reusing it
alone can lose that small arc. The derivation explains both cases.

No epsilon changes coincidence. Oblique horizon rounding can therefore
select a different revolution near an analytically exact contact. An arc
that rounds to a complete turn is a numerical refusal, never a zero-arc
contact. Tests distinguish those refusals from representable near-full
turns and preserve tiny positive arcs.

Every target currently requires the crossing semi-arc domain of M3.
Tangencies, circumpolar points, geographic poles and celestial poles retain
their typed sphere refusals. Applying that domain to meridians is an
explicit project restriction: circumpolar meridian contacts can exist.
No cusp, fallback system or alternate converse construction is invented.

## API and engine integration

The solver requires an explicit target, motion and prepared equatorial
coordinates. It returns the construction name, arc and frozen intermediate
geometry. Strict runtime tests reject unknown fields, accessors, omitted
choices and mixed motion settings. Compile checks verify required fields
and readonly metadata. Results retain no mutable input objects.

A synthetic natal adapter integration check verifies preservation of the
engine's RAMC, latitude, right ascension and declination. It is an
integration check, not evidence for the engine's astronomical accuracy or
an independent directional arc. Ecliptic projection, body contacts, aspects,
timing keys and the final hit API remain later milestones.
