# DE440

From 1.1.0-rc.9 the engine computes on JPL's DE440 by default, and from
1.1.0-rc.10 `calc()` and `birthWindow` do too, and no fallback is silent. The package
ships a sealed pack of Chebyshev series refitted from DE440 for 1790 to 2210,
and a plain call in the root entry, `natalChart`, `positions` and the
functions built on them, takes the Sun, the Moon, the planets and the true
node from it. Nothing is opened, supplied or fetched by the caller, and no
environment variable is read:

```ts
import { natalChart } from "@zodiacs/engine";

const chart = natalChart({ utc: "1990-04-15T08:30:00Z", latitude: 51.5, longitude: -0.12 });
chart.ephemeris; // { name: "jpl-de440", version: "51428874..." }
```

Outside the pack's years, and for what is listed under *The default
source* below, the engine computes on astronomy-engine, as every release
through 1.1.0-rc.7 did everywhere, and the result says so: it names
astronomy-engine, and where that is a fallback it carries a flag. `@zodiacs/engine/de440`
opens a pack the caller supplies, and the root's `withEphemeris` puts such a
source in place of the default. zodiacs.org's hosted compute API uses a DE440
source on its server (its programme unit P4.1).

## The default source

A call outside `withEphemeris` chooses its ephemeris once, from the instant's
Terrestrial Time:

- **The shipped pack**, when the instant is at least one day inside each end
  of the pack's coverage, which runs from the start of 1790 to the start of
  2210 (TDB): so from 1790-01-02 to 2209-12-31 at least. `defaultEphemeris()`
  gives the two ends as days of TT from J2000.0. The day keeps a position, its
  two speed samples (86.4 seconds each side, six hours for the true node) and
  the light-time lookback inside the pack, so one result never mixes two
  ephemerides. The chart names the pack: `chart.ephemeris` is
  `{ name: "jpl-de440", version: <the pack's SHA-256> }`, and its receipt is
  a DE440 receipt (*Within the engine*).
- **astronomy-engine 2.1.19, the fallback**, at every other instant inside
  `EPHEMERIS_SPAN`. The chart says so twice: `chart.ephemeris` is
  `{ name: "astronomy-engine", version: "2.1.19" }`, and its `flags` end
  with `"outside-de440-span"`. Its receipt names astronomy-engine and
  carries the flag. These are the positions 1.1.0-rc.7 computes, to the bit,
  with the error limits `docs/calc.md` gives.

The fallback is also used:

- after `setDefaultEphemeris("astronomy-engine")`, at every instant, until
  `setDefaultEphemeris("de440")`. It is one setting for the whole module; set
  it once, before computing. An application whose stored values were computed
  by an earlier release, or that replays an astronomy-engine receipt, sets
  it;
- if the pack cannot be opened: its bytes are not the sealed pack's (the
  engine hashes them with its own SHA-256, `src/de440/sha256.ts`, and checks
  the pack's trailer, before reading a position), or the runtime has no
  `atob`. The engine does not throw for this. `defaultEphemeris().de440` then
  has `opened: false` and the reason in `error`, and every result is
  astronomy-engine's and says so: it names astronomy-engine and carries the
  flag `"de440-unavailable"`.

**No fallback is silent** (from 1.1.0-rc.10; in 1.1.0-rc.9 the only sign was
that `chart.ephemeris` was absent). Two flags, the type `EphemerisFallback`:

| flag | when |
| --- | --- |
| `"de440-unavailable"` | the default is the pack and the pack could not be opened: its bytes are missing, their SHA-256 is not the sealed pack's, or they cannot be decoded |
| `"outside-de440-span"` | the default is the pack, the pack opened, and an instant the result was computed at is outside it, less a day at each end |

Where they appear, last in each list: `chart.flags` (`natalChart`, the calc
entry's `chart`, and every chart inside `transits`, `synastry` and the
opt-in entries); `flags` of `calc()` and `events()`; a birth window's
`flags` (`"de440-unavailable"`; a window lies inside the pack's years); the
`flags` of the timing and techniques entries' results; `flags` of
`saturnReturn` and of a complete `searchLongitudeCrossings`, which also
report a search that runs past an end of the pack; and a natal receipt's
`resultFlags`. And every result names its ephemeris: `chart.ephemeris` is on
every chart; each `BodyPosition` has `ephemeris` (the name) and, on a
fallback, `fallback` (the flag), so `positions()`, `transits().positions`
and `progressedBodies()` say so row by row; `moonPhase()` has the same two
fields; a calc receipt has `engine.ephemeris`; a birth window has
`ephemeris`. After `setDefaultEphemeris("astronomy-engine")`, the caller's
own choice, a result names astronomy-engine and carries no fallback flag;
inside `withEphemeris` it names the source. `findLongitudeCrossings` returns
bare crossings and cannot say: use `searchLongitudeCrossings` where it
matters. An application that must have DE440 can also check
`defaultEphemeris().de440.opened` once.

A caller may echo a fallback flag in a birth's `flags` only where the
calculation derives it. A supplied chart may carry one only if it names
astronomy-engine, or, as a chart from an earlier release, names nothing. A
natal record with one is refused by an engine before 1.1.0-rc.10, as an
unknown flag.

A search that crosses an end of the pack (a crossing search from
1789 to 1791, say) reads astronomy-engine on one side and DE440 on the other,
and the two differ by up to astronomy-engine's own error there (tens of
arcseconds for the outer planets), so an event within a day of 1790-01-02 or
2209-12-31 TT can be displaced or missed; `searchLongitudeCrossings` flags
such a search `"outside-de440-span"`. Run it after
`setDefaultEphemeris("astronomy-engine")` to have one ephemeris throughout.

**What follows the default.** The root's `positions`, `natalChart` and the
functions built on them (transits, synastry, points, declinations,
progressions, returns), the crossing searches and `moonPhase`, and the opt-in
entries that build on the root's functions (`./timing`, `./techniques`, and
what `./vedic` and `./sky` do not compute on astronomy-engine themselves,
below).

**The calc and window entries, from 1.1.0-rc.10.** `calc()` takes from the
default source what `natalChart()` takes from it: the apparent geocentric
place of the Sun, the Moon and Mercury to Pluto, and the true node and its
opposite point, in each of its eight frames; `chart()` and `events()` follow
`natalChart()` and the crossing search; `birthWindow` partitions on the same
source, so each cell holds what a lone `natalChart()` gives. A default
`calc()` position is `positions()`'s to the bit again. In 1.1.0-rc.9 they
stayed on astronomy-engine and could differ from the root by up to 29.19″.
`docs/calc.md` (*Which ephemeris*, *Bounds*) has the bounds such a position
quotes: measured against Horizons at the 240 L1 vectors for the position,
and none for its distance, its speed or the true node.

**What does not follow it**, and why. Each of these computes on
astronomy-engine whatever the default, and its result or receipt names it:

- `calc()` for a heliocentric, barycentric or topocentric center, an
  astrometric or geometric correction, or the Earth. The pack's reduction
  makes the apparent geocentric place only; these are defined by
  astronomy-engine's own steps and their bounds were measured on it. A
  second reduction and new comparisons with an arbiter would be needed.
- the sky entry's rising, setting and planetary hours, which iterate on
  astronomy-engine's equatorial coordinates and distances, with tolerances
  measured on them;
- the vedic entry's star-anchored ayanamsas, which take the Earth's velocity
  and the Sun's place for a star's aberration and elongation, and
  `vargaSensitivity`, which takes rates from astronomy-engine's vectors.

`natalChart()` gives none of these quantities, so none disagrees with it;
but they rest on another ephemeris than the default positions do, and say
so. The mean node, the mean south node, Black Moon Lilith, the angles and
the houses use no ephemeris.

**Birth-time windows on the pack.** The pack is a series of Chebyshev fits.
Where a read passes from one record to the next, two fits meet within the
pack's budget and not exactly: across the 96,049 such instants from 1800 to
2200 the true node steps by up to 1.11″, the Moon by up to 0.0011″ and the
Sun and the planets by under 0.00025″
(`docs/evidence/1.1.0-rc.10-20261114/results/window-pack-seams.json`). Inside
a record the true node is smooth: over 3,000 consecutive milliseconds at each
of 29,220 epochs it stays within 4.5e-12° of a quadratic
(`results/window-node-jitter-de440.json` there). The window search's bounds
describe smooth motion, so it treats each such instant as a seam, as it
treats a leap second: the source's `steps(fromTtDays, toTtDays)` lists them
(for each record boundary: the boundary, a minute either side, where the
Earth-Moon barycentre's acceleration is differenced, and for each body the
instant whose light left it at the boundary), a few in 48 hours.

The search's rate bounds do not hold near the Sun either. The reduction
bends light by the inverse of the angle from the Sun, with no cut at the
Sun's limb, so a planet passing behind the Sun moves far faster in
`natalChart()` than the body does. The hourly to daily rate scan on the pack
(`results/window-rate-bounds-de440.json`) finds Neptune at 0.142° a day on
1920-08-04, 1.85 times its bound of 0.077, where astronomy-engine's largest
was 0.038; ten-second differences around its closest approach, 0.022° from
the Sun's centre on 1920-08-03, reach more than ten times the bound
(`src/window-de440.test.ts`). Saturn's and Uranus's rates jump between
daily samples near the Sun too: the scan's ratio of bound to largest rate
plus what the grid can miss is 1.48 and 1.45 for them, where the other
bodies keep 1.92 to 2.06. On the pack the
search adds to the bound of Mercury to Pluto, within a degree of the Sun in
longitude, what the deflection allows at the least elongation the interval
can reach (`Sky.rate` in `src/window.ts`), and within 0.01° of the Sun's
centre it compares single milliseconds, which can exhaust its budget:
`WindowBudgetError`, not a wrong answer. A place that close to the Sun is
the reduction's formula, not an observable.

**Cost.** The first call that needs the pack decodes its base64 text and
hashes its 2,489,664 bytes twice, synchronously; later calls reuse the opened
source. The time that takes was not measured for this candidate. An
application that bundles the root entry now bundles the pack's 3,319,552
characters (*The shipped pack*).

With a pack of the caller's own:

```ts
import { readFileSync } from "node:fs";
import { natalChart, withEphemeris } from "@zodiacs/engine";
import { openDe440Pack } from "@zodiacs/engine/de440";

const source = await openDe440Pack(new Uint8Array(readFileSync("de440-1790-2210.v2.zeph")), {
  expectDigest: "51428874d9a47213abc0ff42cbcec65f338624eaa2d8831f0e6ddc3654bf1fa7"
});
const chart = withEphemeris(source, () => natalChart({ utc: "1990-04-15T08:30:00Z", latitude: 51.5, longitude: -0.12 }));
chart.ephemeris; // { name: "jpl-de440", version: "51428874..." }
```

## The pack

A pack is not DE440's own series. The research runtime's compiler 2.0.0
(zodiacs.org's repository, `examples/precision-alpha/tools/compiler/compile.mjs`,
then `tools/seal.mjs`) refits NAIF's `de440.bsp` (SHA-256
`a4ce9bf9b3282becc9f4b2ac3cebe03a2ae7599981aabd7265fd8482fff7c4b5`) body by
body as Chebyshev series on records of its own and stores their coefficients
quantised, each body within an error budget that its header states with the
error the compiler proved for it. Compiled with `--fromYear=1790
--toYear=2210` and sealed, the pack is 2,489,664 bytes with the SHA-256 above
(zodiacs.org's P4.2 record and its Linux rebuild:
[evidence/de440-20261110/README.md](evidence/de440-20261110/README.md)). Its
header gives budgets of 0.01 km for the Moon, 0.3 km for the Sun, the
Earth-Moon barycentre, Mercury and Venus, 0.5 km for Mars and 1 km for Jupiter
to Pluto, and proven position errors of 0.0086 km for the Moon and 0.26 to
0.97 km for the others ([pack-accuracy.json](evidence/de440-20261110/pack-accuracy.json),
`packBodies`).

## The shipped pack

The package carries that pack, byte for byte (first in the withdrawn draft
1.1.0-rc.8, then in 1.1.0-rc.9). The root entry opens it as its default
source; `@zodiacs/engine/de440/pack` gives it to a caller:

- `DE440_PACK` describes it: its file name, its SHA-256, its 2,489,664 bytes,
  the years it was compiled for (1790 and 2210; its coverage runs from the
  start of 1790 to the start of 2210, TDB) and the kernel's name and SHA-256.
- `de440PackBytes()` gives the bytes, a new `Uint8Array` at each call,
  unchecked.
- `shippedDe440Source()` opens them with `openDe440PackSync`, expecting
  `DE440_PACK.sha256`, and returns the source, the same one at each call and
  the one the root's default uses. `openShippedDe440Pack()` gives the same
  source as a promise. Neither needs WebCrypto. Handed to `withEphemeris`,
  the source refuses an instant outside the pack with a `De440Error`
  (`out-of-coverage`), where the default falls back.

A package of JavaScript modules has no portable way to carry a binary file to
every runtime and bundler, so the bytes are base64 text: 3,319,552 characters
for the pack, once, in one shared chunk under `dist/` that the root's
ephemeris chunk and `dist/de440-pack.js` both import, and in no other file.
They decode in memory when the source is first opened.
`scripts/build-de440-pack.mjs` writes their source, `src/de440/pack-data.ts`,
from the sealed pack and refuses any other bytes;
`scripts/verify-package-contents.mjs` checks that one built file holds the
pack once, with that digest, and names the entries whose graphs load it: the
root, `./calc`, `./internal`, `./sky`, `./techniques`, `./timing`, `./vedic`,
`./window` and `./de440/pack`. The entries that load no ephemeris
(`./crossings`, `./deltat`, `./time`, `./lite`, `./conventions`,
`./receipt`), `./geo`, `./houses`, `./internal/math` and `./de440` itself do
not load it.

The pack makes the package much larger than 1.1.0-rc.7: 4,539,239 bytes
unpacked in 98 files (1.1.0-rc.10) against 1,152,017 in 94, 3.9 times, of
which 3,319,552 are the pack's text
([evidence/1.1.0-rc.10-20261114/sizes.json](evidence/1.1.0-rc.10-20261114/sizes.json),
which also gives the packed sizes and sets the candidate beside 1.1.0-rc.9; `artifacts/README.md` records the
archive's). Every install downloads it, and every application that bundles
the root entry, or one of the entries above, carries those 3,319,552
characters. The pack's quantised coefficients compress little: gzip at its
highest level takes those characters only to 2,357,278 bytes (Node's zlib;
the same file).

Against an arbiter that is not this engine: at the 240 L1 vectors of the
conformance suite, JPL Horizons's apparent geocentric places from DE441 at 24
TT instants from 1851 to 2148 for the Sun, the Moon and the planets (Mars to
Pluto as barycentres), carried into the IAU 2006/2000A true ecliptic of date,
a plain `natalChart`, on the default source, is within the suite's 1″ in
longitude and in latitude at all 240. The largest differences are 0.0127″ in
longitude and 0.0011″ in latitude, both the Moon's
(`src/de440-default.test.ts` enforces all three figures for a plain call and
`src/de440-pack.test.ts` for the same source through `withEphemeris`;
`conformance/RESULTS.md`; and, on the package installed from its archive,
`docs/evidence/1.1.0-rc.10-20261114/`, where the largest are 0.0126″ and
0.0010″, and `calc()` and `birthWindow` are scored on the same vectors). The arbiter's own check puts the lunar difference
between DE440 and DE441 at up to 12.63 mas in 1851
(`conformance/arbiters/l1/README.md`). The fallback, astronomy-engine, passes
48 of the 240, with differences up to 18.8″ in longitude and 19.1″ in
latitude (the suite's second section). Those 240
places say nothing of the true node, of speeds, or of instants outside 1851
to 2148.

Whether data refitted from DE440 may be redistributed rests on the owner's
position that DE440 is JPL's public data, not on a statement of JPL's or
NAIF's: NAIF's rules permit redistributing its kernels unmodified and do not
speak of data refitted from one, and the question 1.1.0-rc.3 recorded as put
to NAIF has no answer in this repository (`LICENSING.md`, *DE440 pack*).
Zodiacs.org made the pack; JPL and NAIF have not reviewed or endorsed it.

What the refit costs, measured on that pack by
[tools/pack-accuracy.ts](evidence/de440-20261110/tools/pack-accuracy.ts), the
reduction below on the pack against the same reduction on the raw kernel, at
20,001 instants evenly spaced from 1800 to 2200 TT and either side of every
edge of the pack's records, where a refit errs most: the Moon's place differs
by at most 0.0016″, Venus's by 0.0008″, every other body's by at most
0.0005″; the true node by at most 0.84″, at an edge of the Moon's records
(median 0.0031″ over the evenly spaced instants), because it is formed from
the Moon's velocity, which the refit carries less closely than its position.
At the 200 instants of the ERFA oracles the pack's places are within 0.00094″
and its node within 0.066″ of the chain's. zodiacs.org's tier B checks the pack it
builds against those oracles.

`openDe440Pack(bytes, { expectDigest })` copies the bytes, hashes the whole
file (WebCrypto; without it, a TypeError) and refuses it with `De440Error`
code `digest-mismatch` unless the SHA-256 is `expectDigest`; it then checks
the pack's own trailer against its contents and the header's numbers that it
reads (sizes, offsets, encodings, spans) before reading through it. It
refuses six-byte quantised fields, which the research runtime's reader
decodes wrongly; the pack above has none.

## The reduction

`src/de440/reduce.ts` is the research runtime's reduction with its shipped
options (zodiacs.org's `examples/precision-alpha/src/core/` at site commit
4fa9ffbf), ported operation for operation so that the two give the same
numbers; zodiacs.org's check C9 compares them:

- TT to TDB by the Astronomical Almanac's three-term form;
- light-time by iteration, at most 12 steps, to 1e-11 s;
- deflection of light by the Sun, in ERFA's `eraLd` form, with the Sun at
  reception for the observer's direction and at emission for the source's,
  and a limiter of 1e-14 (none for the Sun itself);
- relativistic annual aberration (`eraAb` without its gravitational term),
  the Earth's velocity from the Chebyshev derivative;
- frame bias and IAU 2006 precession (Fukushima-Williams angles), IAU 2000B
  nutation with the P03 adjustment (the 77 terms, fundamental arguments and
  planetary offsets of `src/nutation.ts`), and the true obliquity, to the
  ecliptic and equinox of date.

The geocentric Moon is MoonRelEMB(t − τ) − EarthRelEMB(t) + [EMB(t − τ) −
EMB(t)], the bracket as −vτ + aτ²/2 from the Earth-Moon barycentre's velocity
and acceleration at t, so that the barycentre's 30 km/s never multiplies the
rounding of the epoch t − τ, as zodiacs.org's preregistration of P4.1 (site
commit 5305fc74) specifies. Mars to Pluto are planetary-system barycentres,
not planet centres.

The true node is the ascending node, on the true ecliptic and equinox of date,
of the plane of r × v, where r and v are the Moon's geometric geocentric
position and velocity in the ICRF from the pack; the South Node is 180° from
it.

On the raw kernel (through the test-only reader `src/de440/kernel.testkit.ts`),
this reduction is within 1e-6″ of the ERFA chain at the oracles' 200 instants,
place and node alike (`src/de440-kernel.test.ts`). That figure is the
reduction's; what the entry gives is that plus the pack's refit, above.

A source refuses an instant outside its pack with `De440Error` code
`out-of-coverage`, not with the RangeError the root gives outside
`EPHEMERIS_SPAN`, and so does an instant whose light-time lookback or speed
samples (±0.001 day for a body, ±0.25 day for the nodes) fall outside it: the
first and last hours of the pack's span are refused for those bodies.

## Within the engine

`withEphemeris(source, fn)` runs `fn`, which must be synchronous and must not
return an iterator, with the root's body positions from `source` in place of
the default source:
`positions`, `natalChart` and the functions built on them (transits,
synastry, points, declinations, progressions, returns), the crossing searches
and `moonPhase`. It restores the source before, whatever happens, and calls
nest. The angles and the houses do not depend on the ephemeris and are
computed as before; speeds are the same central differences.

The functions that compute positions from astronomy-engine themselves, or
whose bounds were measured on it, refuse with a TypeError inside
`withEphemeris`, rather than mix two ephemerides or name the wrong one in a
receipt: the calc entry (`calc`, `chart`, `events`), the sky entry's rising,
setting and planetary hours, the vedic entry's star-anchored ayanamsas (and
the sidereal charts on them) and `vargaSensitivity`, and the window entry's
`birthWindow`. Outside `withEphemeris` they run: the calc and window
entries on the default source, the others on astronomy-engine (*The default
source*). The other opt-in entries build on the root's functions and
follow the source.

A chart computed inside, like every chart from 1.1.0-rc.10, names its
ephemeris in `chart.ephemeris`, and for a DE440 source
`createNatalEnvelope` writes the receipt for it: the DE440 conventions set (the
last of `NATAL_RECEIPT_CONVENTION_SETS`), the ephemeris `jpl-de440` with the
pack's SHA-256 as its version, and the required feature
`ephemeris-jpl-de440`, so that an earlier engine refuses the record. A
provenance claim about the ephemeris must then name the same pack.
`createNatalEnvelope` takes `chart.ephemeris` as given, as it takes the rest
of a chart: a chart's data is not authenticated. `natalReplayInput` gives the
chart's input; to recompute a DE440 record, run it on a source whose
ephemeris version is the receipt's: a plain call, when that is the shipped
pack's, or inside `withEphemeris`. To recompute an astronomy-engine record of
an instant inside the pack's years, call
`setDefaultEphemeris("astronomy-engine")` first.
