# M8 validation record

This session adds bounded HTTP admission to the existing optional service.
A per-address token bucket uses a monotonic clock, with configurable burst,
refill, tracked-client count and idle cleanup. Separate active-request and
TCP connection bounds prevent an unbounded admission queue. Rate rejections
return private structured errors with HTTP 429 and a conservative Retry-After;
work or client-table overload returns HTTP 503 with a retry hint.

Admission precedes body parsing, lookup and provider execution, including
Expect requests. Accepted work occupies a slot through response completion.
If a caller disconnects during provider execution, the slot remains occupied
until that provider settles. Validation errors and provider exceptions free
work slots after completion but do not refund rate tokens. Arbitrary provider
code cannot be cancelled by the transport.

Idle cleanup never removes a partially exhausted bucket or one with active
work. A full table rejects new identities rather than resetting an existing
client's limit. Cleanup scheduling begins only after listening, uses an
unreferenced timer, and ends at close. Close also clears stored addresses.
The controller's diagnostic snapshot contains aggregate counts only.

The default client identity is the socket IP. Forwarding is opt-in through
an explicit bounded list of exact trusted proxy IP literals, copied at
construction. IPv6 canonicalization and mapped IPv4 prevent spelling-based
bucket splits. A single bounded X-Forwarded-For chain from a trusted immediate
peer is walked towards the caller, stopping at the first untrusted address.
Other peers' forwarding claims are ignored. Malformed or duplicate fields
from trusted proxies are rejected privately. Forwarded and X-Real-IP are
ignored. The launcher validates and passes through rate, resource and trust
options without loading an index for malformed configuration.

No place, atlas or engine resolver is changed or copied. Existing transport
tests continue to preserve atlas precedence, citations and uncertainty, and
the existing IANA policy and metadata. The pure library entry does not import
the HTTP module, admission controller, proxy identifier or service launcher.

## Checks and reference scope

[http-admission.test.ts](../tests/http-admission.test.ts) uses a controlled
millisecond clock to check burst exhaustion, fractional refill, exact recovery
boundaries, long-idle refill caps, backwards-clock clamping, independent
clients, bounded table growth, full-table refusal, safe eviction, active
work retention, idempotent release/close and malformed configuration.
Defaults documented in the README are asserted in these tests.

[http-client.test.ts](../tests/http-client.test.ts) checks synthetic IP
identities and proxy chains, canonical spellings, mapped IPv4, untrusted
forwarding, first-untrusted-hop selection, trust snapshots, duplicate fields,
malformed literals, and configured-list and chain bounds. It accepts no
wildcard, hostname, port, zone identifier or CIDR trust rule.

[http-limits.test.ts](../tests/http-limits.test.ts) checks actual loopback HTTP
responses with synthetic queries and controlled refill timing. It covers a
shared burst across both routes and simultaneous requests, concurrent direct
clients on distinct loopback addresses, proxy-spoofing resistance, full-table
recovery, periodic cleanup, work overload, aborted provider/body requests,
error recovery, Expect admission, TCP connection rejection and timer cleanup.

[http-service.test.ts](../tests/http-service.test.ts) retains the attributed
sample's atlas/IANA transport checks and adds launcher option validation,
configured burst exhaustion and trusted-proxy client separation under both
termination signals. Help still runs with network entry points blocked.
The existing preload guard is a regression check, not a network sandbox.

These tests verify operational behavior on the tested inputs. They do not
measure sustained throughput, distributed rate limiting, resistance to
arbitrary denial-of-service traffic, or geographic/historical accuracy.
Limits are per service instance and per IP; callers behind a shared address
share capacity. A trusted proxy must overwrite or append the actual peer
address and must be controlled by the operator. TCP connection rejection
and some transport deadlines can close a connection without an HTTP JSON
response. Pending provider code still depends on that provider to settle.

The Node HTTP behavior used for Expect handling is documented in
[the Node HTTP reference](https://nodejs.org/download/release/v22.22.2/docs/api/http.html#event-checkcontinue):
listening for checkContinue makes the application responsible for accepting
or rejecting the request before sending a continue response. Connection
admission uses
[Node server.maxConnections](https://nodejs.org/download/release/v22.22.2/docs/api/net.html#servermaxconnections)
in a standalone process. Monotonic default refill uses
[Node performance.now](https://nodejs.org/download/release/v22.22.2/docs/api/perf_hooks.html#performancenow).
