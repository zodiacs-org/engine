# M11 validation record

This session adds a runnable synthetic example that prepares input for the
existing engine, plus an operations guide. It changes only `geocode/`.
Historical rules, atlas data, the atlas resolver, engine geo API and the
attributed GeoNames sample remain unchanged. No chart math is added.

## Engine handoff

[examples/engine-input.ts](../examples/engine-input.ts) uses the composed
geocoder and the engine's existing `BirthInput` type through a relative
type import. It preserves the complete geocode answer next to its handoff.
The helper is example application policy, not an exported library API.
It requires a selected place, a supplied clock time and an `ok` time answer.
Atlas answers additionally require the native `documented` uncertainty flag.
Gaps, folds, unavailable clocks or zones, inferred/uncertain readings,
unknown times and unresolved places require review and contain no engine
input. It does not bypass the atlas or resolve an atlas comparison zone.

Ready atlas answers keep the native instant and atlas coordinates. Ready
IANA answers use detached native Dates and flags and the selected place's
coordinates. The example chooses whole-sign houses and the engine's existing
UTC input setting explicitly. The engine retains its own pre-UTC time basis
and calculation limits; the helper does not implement those conversions.
Elevation, attribution, rule versions, citations and provider metadata remain
in the retained geocode answer. They are not represented by `BirthInput`.

[examples/run.mjs](../examples/run.mjs) uses scoped TypeScript loading, as
the existing launchers do, and accepts an explicit local index. It emits a
single JSON document with invented queries. It needs no root build or engine
ephemeris dependency installation and does not calculate a chart. The README
also shows the consuming application's call to the installed engine's
`natalChart`; that chart calculation is outside this example's validation.

[tests/engine-example.test.ts](../tests/engine-example.test.ts) checks sample
resolution, atlas coordinate precedence, missing/unsupported zones, refusals
and review outcomes. Its IANA inputs are compared with `resolveLocalBirth`
from the existing engine geo entry without a longitude override. A subprocess
runs the actual launcher from another working directory with common Node
network APIs blocked. The same guard already has its own checks in the CLI
suite. This is a Node API regression guard, not an OS network sandbox.

These tests establish application handoff and snapshot isolation on their
invented queries. They are not independent geographic, historical or
astronomical accuracy evidence. The earlier independent timezone checks
and their reference limitations remain in [M9.md](M9.md).

## Documentation and operation checks

[OPERATIONS.md](../OPERATIONS.md) connects sample setup, place selection,
date-only inputs, CLI outcomes, explicit library loading, service operation,
rebuilding, attribution and privacy. The existing README continues to define
API contracts, byte/rate bounds and provider limitations with links to the
enforcing tests. The guide adds no measured accuracy, memory or throughput
claim. It distinguishes local data operations from explicit source downloads
and explains the limits of the sample, source assignments and older histories.

[check-m11-operations.mjs](check-m11-operations.mjs) runs the sample receipt
check and documented build command into a fresh ignored temporary directory.
It runs the example and guide's CLI queries with Node network APIs blocked,
checks their unresolved outcomes, starts the existing server on loopback,
compares the guide's lookup and timezone request fields with CLI answers,
checks no-store output and shuts down through SIGTERM. It removes its sample
in cleanup. It emits only outcome summaries, not a new place or timezone
dataset. [m11-operations.txt](m11-operations.txt) records the successful run.
HTTP requests use Node fetch with the guide's curl-equivalent request fields;
the curl executable and external deployment infrastructure were not tested.
Source acquisition remains covered by the existing builder/acquisition tests;
this session does not refresh the upstream sample or download a new city dump.

The privacy documentation describes the implemented absence of request logs
and result files, transient address storage and response cache headers. It
also notes that clients, shell history and proxies can persist inputs, GET
queries appear in URLs, output includes civil inputs, and the tiny service
has no authentication or TLS layer. No personal records or credentials are
used in examples or validation.

## Commands and results

From `geocode/`, with the project's supported Node runtime on PATH:

```sh
npm run check
node evidence/check-m11-operations.mjs
python3 scripts/select-sample.py --check
node ../atlas/tools/check.mjs
node --test ../atlas/tools/selftest.mjs
```

[m11-checks.txt](m11-checks.txt) records the full TypeScript/Vitest/scope check
and the unchanged atlas checks, including runtime versions. The operation
record separately identifies host ICU and tz versions. The existing
independent IANA suite rebuilds its references using its verified cached
archives. No new accuracy claim is derived from this engine's own output.

The scope gate checks candidate file sizes, absence of em dashes in
documentation and exclusion from the engine package via npm dry run.
Root build, package size and archive rebuild gates need a separate root
setup and remain outside this session's authorized write scope. No packed
file, root configuration, release archive, engine source or git metadata is
changed. The owner's existing untracked `SCOPE-CHANGE.md` remains untouched.
Only M11 is completed; M12 remains for the next session.
